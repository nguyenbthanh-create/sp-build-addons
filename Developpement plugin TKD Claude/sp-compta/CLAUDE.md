# CLAUDE.md

Guide pour Claude Code sur ce dépôt.

## Quoi

Plugin WordPress `sp-compta` : gestion de trésorerie associative (dépenses, recettes, devis, factures, clients, fournisseurs, sponsors). Entièrement séparé de [../sp_build](../sp_build) — aucune dépendance à ses tables, classes ou rôles. Spec fonctionnelle complète : [../md/spec-fonctionnelle-module-compta.md](../md/spec-fonctionnelle-module-compta.md). **Avant de déboguer un comportement étrange, consulter [correctif.md](correctif.md)** — journal des bugs déjà rencontrés et de leur cause racine, pour ne pas reparcourir le même diagnostic.

## Contraintes d'environnement

Pas de binaire PHP, pas de WordPress local dans ce sandbox (même limitation que sp_build). Les tests sont écrits (TDD) mais **non exécutés ici** — à lancer via `composer install && vendor/bin/phpunit` sur un environnement avec PHP + [wp-phpunit](https://github.com/wp-phpunit/wp-phpunit) (ex. le site de test OVH), variable d'env `WP_TESTS_DIR`.

**Déploiement (production/test) : pas de Composer requis.** Le plugin charge ses classes via un autoloader natif (`spl_autoload_register` dans [sp-compta.php](sp-compta.php)), pas `vendor/autoload.php` — cohérent avec le fonctionnement "sans outillage" de [sp_build](../sp_build). `composer.json`/`vendor/` ne servent qu'au développement (tests PHPUnit, phpcs), jamais copiés sur le site. **Le plugin requiert PHP >= 8.0** (property promotion utilisée partout) — à vérifier sur le site cible avant activation (Outils → Santé du site dans wp-admin, ou panneau d'hébergement OVH).

## Conventions de ce plugin

- **PSR-12** pour le style de code (voir [phpcs.xml](phpcs.xml)), **PSR-4** pour l'autoload (`SpCompta\` → `src/`). Namespaces et camelCase, pas les conventions snake_case/procédurales de sp_build.
- **TDD + BDD** : un test PHPUnit par comportement, structuré en commentaires `// Given / // When / // Then`. Le test s'écrit avant l'implémentation. Les scénarios sont aussi documentés en Gherkin dans le `.md` jumeau de la classe testée.
- **Un `.md` jumeau à côté de chaque `.php`** (même nom, même dossier) : rôle de la classe, API publique, scénarios BDD couverts, et une section "En cas de bug" avec les pistes de diagnostic les plus probables — pensé pour une lecture rapide en cas d'anomalie, sans avoir à relire tout le code.
- **Un repository par entité** pour l'accès SQL (`src/Repository/`), une entité immuable par table (`src/Entity/`) — voir [src/Repository/FournisseurRepository.php](src/Repository/FournisseurRepository.php) comme patron de référence pour les entités futures (`Client`, `Depense`, `Recette`, `Devis`, `Facture`, `Sponsor`).
- **Accès** : toujours garder par `Capabilities::currentUserCanManage()` (voir [src/Capabilities.md](src/Capabilities.md)) — capacité `sp_compta_manager` dédiée, pas de réutilisation des rôles sp_build.
- **Nom de table** : toujours via `Database::table*()`, jamais en dur (voir [src/Database.md](src/Database.md)).

**08/09/2026, suite — bug réel trouvé et corrigé** : `Categories::DEPENSE`/`RECETTE` ont des clés (`'60'`, `'74'`...) que PHP convertit automatiquement en `int` — `libelleCategorie()`/`libelleSousCategorie()` déclarées `string $code` strict levaient une `TypeError` fatale dès qu'on itérait sur le référentiel avec `foreach`, coupant net les pages Dépenses/Recettes.
